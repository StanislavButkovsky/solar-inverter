# Где мы остановились

Точка входа для новой сессии. Состояние на **09.09.2026**, после первой
серии работ. Здесь только то, что нужно, чтобы продолжить, — почему всё
устроено именно так, написано в [DOCS.md](DOCS.md).

---

## Одной строкой

Модуль мониторинга солнечной системы на ESP32: читает батарею и инвертор,
показывает веб-страницей в домашней сети. **Первое устройство работает
и висит в сети**, второе и третье написаны и собираются, но ждут плат
ESP32-S3 и драйвера USB-хоста.

---

## Три устройства

| # | Инвертор | Как читаем | Протокол | Состояние |
|---|---|---|---|---|
| 1 | **SD-HYM-4862HWP** | Bluetooth через донгл Eybond | Modbus RTU 9600, адрес 1 | **работает**, ждёт привязки донгла |
| 2 | **Hiden Control HS35-5648PRO** (= MUST PV18 Pro) | USB через мост CH340 | Modbus RTU 19200, адрес 4 | код готов, нужен драйвер USB |
| 3 | **ASTERION PLUS 5.6K** (= Voltronic Axpert VM) | USB | текстовый: `QPIGS`, `QMOD`, `QPIWS` | код готов, нужен драйвер USB |

Батарея первого — **DALY Smart BMS 14S NMC**, читается отдельно по Bluetooth.
У второго и третьего батарея штатная, своего канала не имеет: её состояние
приходит из регистров самого инвертора.

---

## Что работает прямо сейчас

Плата **ESP32-D0WD-V3 (WROOM)**, MAC `20:9b:a9:68:af:e4`, в домашней сети.

```
адрес       http://192.168.1.93   (и http://solar.local)
сеть        GKV_169_1
точка доступа  solar-setup / 12345678 → http://192.168.4.1
терминал    /dev/ttyUSB0, 115200
```

**Модуль питается от USB компьютера.** Отключили кабель — он выключился,
и по сети не ответит. Если `192.168.1.93` молчит, первым делом проверить,
воткнут ли он вообще: на том же порту периодически оказывается плата
от другого проекта (LoRa, отзывается строками `EVT LORA_RX` и `[Beacon]`) —
её не трогать. Своя плата опознаётся так:

```bash
~/.platformio/penv/bin/python ~/.platformio/packages/tool-esptoolpy/esptool.py \
  --port /dev/ttyUSB0 chip_id      # должно быть ESP32-D0WD-V3, MAC 20:9b:a9:68:af:e4
```

Для постоянной работы модуль нужно питать отдельным адаптером 5 В —
на этапе изделия он должен висеть на AC-выходе инвертора.

Занято 65 % флеша, 19 % RAM. Демо-режим включён (`sim on`), поэтому цифры
на экране нарисованные — с явной пометкой в интерфейсе.

### Готовое в прошивке

* чтение DALY BMS по BLE: заряд, напряжение, ток, ячейки, температуры, защита;
* дашборд: схема потоков мощности на SVG, режим инвертора цветной плашкой,
  сетка ячеек, журнал событий, настройки за отдельной кнопкой;
* журнал событий с временем по NTP: связь потеряна и восстановлена, BMS
  запретила заряд, пропало питание от сети, сменился режим;
* настройка сети: точка доступа с формой, терминал по USB, кнопка BOOT;
* темы оформления, включая переключение по часам; ярлык на главный экран;
* демо-режим с моделированием пропадания сети.

## Что делать дальше

### 1. Привязать донгл первого инвертора — можно сегодня

Модуль уже умеет читать инвертор, но не знает, к чему подключаться.

1. Закрыть приложение SmartESS (донгл держит одно соединение).
2. Открыть `http://192.168.1.93` → Настройки → «Искать устройства, 5 секунд».
3. У найденного донгла нажать кнопку **«инвертор»**.
4. Выключить демо-режим кнопкой на жёлтой плашке.

Дальше смотреть, сойдётся ли карта регистров: профиль `09CB` проверен
сообществом на другой модели, у нас это рабочая гипотеза. Если цифры окажутся
бессмыслицей — подбирать смещения, сверяясь со SmartESS.

### 2. Батарея DALY — когда окажется в пределах Bluetooth

Порядок в `firmware/README.md`, раздел «Порядок первого подключения на месте».
Главное: сверить с официальным приложением **знак тока**, SOC, напряжения
ячеек и остаточную ёмкость. Это единственная проверка смещений, которую
нельзя сделать заранее.

### 3. Драйвер USB-хоста — когда приедут платы

Заказаны две ESP32-S3-DevKitC-1 (N8R2). Нужна ещё третья, если делать
и второе, и третье устройство одновременно.

**Первым делом — `lsusb`** на каждом инверторе:

| Что покажет | Что значит |
|---|---|
| `1a86:7523` | мост CH340, обычный последовательный порт. Драйвер один на оба |
| `0665:5161` | устройство HID, команды восьмибайтовыми отчётами. Нужен второй драйвер |

У HS35 почти наверняка CH340 (так у сообщества). У Asterion скорее HID —
это семейство Voltronic. Разница в объёме работы примерно неделя.

Отлаживать драйвер на столе: тот же чип `1a86:7523` стоит в любом
копеечном USB-UART свистке, инвертор для этого не нужен.

### 4. Переключение режимов — после того как чтение отработает

На HS35 запись доступна и проверена сообществом: режим использования энергии,
приоритет источника заряда, уставки напряжений, ток заряда. На Asterion —
команды `POP`, `PCP`. **Уставки заряда не трогаем**: это отдельный этап
с жёсткими лимитами в коде и watchdog на молчание BMS.

## Устройство кода

Одна кодовая база, три цели сборки. Общего кода больше девяноста процентов.

```
    inv.cpp          цикл: спросить шаг, скормить ответ, повторить
       │
       ├── modbus.cpp / voltronic.cpp     кадр, сумма, склейка из кусков
       │                                  (не знают про провод)
       ├── profile_*.cpp                  что спрашивать и как понимать
       │                                  eybond · must · voltronic
       └── inv_*.cpp                      сам провод
                                          ble · usb
```

```bash
cd firmware
pio run -e esp32dev          # первое устройство
pio run -e esp32s3-hs35      # второе
pio run -e esp32s3-asterion  # третье
pio run                      # все три
pio run -e esp32dev -t upload --upload-port /dev/ttyUSB0
```

Страница живёт в `firmware/web/index.html` — обычный html, правится напрямую;
пре-сборочный скрипт жмёт её в gzip и кладёт в прошивку.

## Что уже стоило времени — не наступать снова

Полный список в [DOCS.md](DOCS.md), раздел «Грабли». Три самых дорогих:

**Прошивка стирала себе настройки.** GPIO0 сидит на схеме автосброса платы:
любая программа, открывшая последовательный порт, прижимает его к земле.
Для кода это неотличимо от удержания кнопки BOOT — и при закрытии порта
срабатывал сброс. Три раза списывалось на порчу NVS. Исправлено верхним
пределом на длительность нажатия.

**NimBLE 1.4 не работает с ядром Arduino 3.x.** Собирается без предупреждений,
плата уходит в вечный ребут на `esp_bt_controller_init`. Нужна 2.x.

**Запуск сканирования прямо в обработчике HTTP** съедает ответ: радио уходит
скакать по каналам, не успев его отправить. Запускать из `webLoop()`.

Отдельно: **мои собственные скрипты чтения порта дублируют вывод** сотнями
строк при плотном цикле чтения. Это артефакт pyserial, а не прошивки.
Для чтения надёжнее `cat /dev/ttyUSB0`, для отправки `printf ... > /dev/ttyUSB0`.

## Открытые вопросы

1. Сойдётся ли карта регистров `09CB` с первым инвертором.
2. Совпадают ли смещения полей DALY с реальностью (знак тока, SOC, ячейки).
3. Что за устройство за USB у HS35 и у Asterion — CH340 или HID.
4. Отдаёт ли HS35 регистры 113/114 (заряд и здоровье батареи) на своей прошивке.
5. Хватит ли одной антенны на два постоянных BLE-канала плюс Wi-Fi —
   смотреть на счётчики разрывов в карточке «Канал связи».
